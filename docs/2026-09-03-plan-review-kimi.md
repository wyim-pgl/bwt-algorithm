# Kimi review of the 12-item work plan (prose only, no file access)

Run 2026-09-03 with the plan inlined and tool use forbidden, so its judgement is about the
plan as reasoning rather than about the repository. Its central finding: a thirteenth item
is missing — pinning a release commit that every shipped table cell traces to.

---

## Findings (most consequential first)

**1. The plan has no answer to "which binary produced which number," and that is the first thing a reproducibility editor will ask.** Three commits are live in this plan: published pairs ran at `07ad6fa`, C-1 is re-measuring at `0363d8b`, and the repo tip is `4aeba8e` with "guard tests green" — a phrase that says nothing about numerical identity across commits. No item in the twelve requires that every shipped table cell trace to a single pinned release commit, or documents a justified exception. The plan even notes `07ad6fa` was "the only commit where Tier 3's window was fixed" — i.e., the published numbers were produced by behavior that no longer exists at tip. Correction: add a thirteenth item before anything ships — freeze a release commit, regenerate or re-verify every table against it (or annotate per-cell provenance in the manifest with the commit hash as a column), and run the pipeline end-to-end from a clean clone at that commit with checksums tying each deposited artifact to each table cell. This is not a refinement; it is absent from the twelve and it is the referee's first question.

**2. Thirty corrections a day with no net underneath them.** The risk profile is not the count; it is that corrections are being applied by the same people, using the same procedures, that produced the errors — proven by the rounding fix that was made by re-doing the rounding. Three failure modes are unguarded: a fix that is itself wrong (already happened once, caught by luck), a wrong source artifact propagating into multiple corrected cells at once, and fixes applied to the manuscript but not to the generating scripts or manifest, so the next regeneration resurrects the defect. The check the plan lacks is a post-correction audit with an independence property: after Group 1 and C-1 land, regenerate every table cell from the deposited artifacts by script and diff against the manuscript, and require every corrected number to be re-derived by a *different path* than the one that produced the fix (different tool, different person, or hand-computation from the raw log — never the same procedure re-run). Add a correction ledger with before-value, after-value, evidence path, and derivation method. Without this, the team is shipping a diff it has never read as a whole.

**3. Group 2's adjudication standard, as sketched, will reproduce the false-positive error in reverse.** The root defect was promoting *absence of an artifact* into *the number is wrong*. "Verified or explicitly rejected, nothing stays in limbo" forces binary verdicts, which means any finding whose artifact is still missing gets resolved by the same move that burned them three times — just with the opposite sign. A legitimate rejection must rest on **positive contrary evidence**, never on absence. Concretely, a rejection record must contain: the finding ID and the claim verbatim; the artifact refuting it (path, file hash, line/row); the exact check performed (command or diff), re-runnable by a stranger; the repo commit at which the check was made; the checker's name; and the date. And the rule must be **symmetric**: a confirmation needs the same record showing artifact and mismatch. Three states, not two — CONFIRMED, REJECTED, BLOCKED-ON-MISSING-ARTIFACT — where absence routes only to the third. Note also that "CONFIRMED" currently lives in neither `quarantine.md` nor `todo.md`; the three false confirmations escaped the evidence rule precisely because confirmations aren't ledgered. Finally, the person adjudicating 31 findings is the same person who produced the day's three false confirmations — the plan contains no redundancy for the human component. Spot-check a sample of verdicts (including all rejections) with a second reviewer.

**4. The ordering argument prices the wrong cost.** A 600-second rehash is noise; treating it as the cost of doing Group 1 twice hides the real risks. First, Group 1 item 2 edits `manifest.tsv:67` claims (the unqualified "1.55x", the stall attribution) that C-1's re-measurement may directly supersede — you would be correcting rows tonight that tomorrow's data reopens. Second, Group 1's items are themselves unadjudicated findings from the same pipeline that produced three false "confirmations" today; editing files before adjudication risks correcting numbers that were never wrong. Third, "unblocks everything else" is false — nothing downstream consumes Group 1's edits except the rehash. C-1's 12–15 h window is free labor time for the read-only work. Do Group 2 and item 6 during the window, then do *all* `results/` edits once, after C-1 lands, with a single rehash.

**5. Deferring the Abstract is backwards, and the deferral itself is a smell.** For an Application Note the abstract is the claim surface — "1.55x" and the stall attribution live there in spirit even when the numbers live in the supplement. Writing it last "against a closed list" assumes the list closes; the adjudication queue and an external dependency say otherwise. Worse, an abstract restructure is a *defect generator*: rephrased claims will mismatch the text and tables in ways that must go back into the ledger, and doing that with zero runway guarantees it doesn't happen. And note the mechanism: "deferred by the author" means the single most claim-sensitive item is routed around the single scarcest resource. Correction: draft the restructured abstract now, in parallel, explicitly as a defect detector; lock the *numbers* last, but not the *structure*.

**6. Item 9 is a submission risk disguised as someone else's task.** "External dependency; tracked, not ours" means two of the main-text figures sit behind a single person with no deadline, no owner on this team, and no fallback. A referee won't care, but the submission deadline will. Assign an owner, a drop-dead date, and an in-house fallback (the team generated the data; a placeholder-grade in-house figure is better than a missing one at submission).

**7. Minor but telling: Group 1 item 1 replaces cost cells from "logs located at `a38201b`."** Given the day's root cause, the replacement numbers should carry the same positive-evidence record demanded of Group 2 verdicts — which log file, which hash, which lines summed to 37:28:39 — recorded in the commit message or ledger, not just in the plan. Otherwise the team has fixed a wrong number with an unverifiable one.
